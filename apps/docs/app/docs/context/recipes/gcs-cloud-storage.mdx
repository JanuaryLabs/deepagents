---
title: GCS Cloud Storage Volumes
description: Persist sandbox files to Google Cloud Storage with either a remote Docker volume or a same-host gcsfuse mount
---

This recipe covers two production paths for persisting sandbox files to **Google Cloud Storage**:

- A **remote Docker daemon** on a GCP VM, where an [rclone](https://rclone.org/docker/) volume plugin backs a named Docker volume. The `@deepagents/context` side uses the standard `type: 'volume'` primitive with `lifecycle: 'external'`.
- A **same-host Linux daemon**, where [gcsfuse](https://github.com/GoogleCloudPlatform/gcsfuse) mounts the bucket on the host and `gcs()` exposes that mountpoint to the sandbox as a typed bind volume.

In both cases, the cloud wiring (plugin, credentials, IAM, and host mounts) stays outside DeepAgents, exactly where [the sandbox docs](/docs/context/docker-sandbox#volumes) say it belongs.

## Remote daemon on a GCP VM

### Topology

In this setup, the agent runs on one server and the Docker daemon runs on a
GCP VM. DeepAgents sends Engine API requests to that VM through the selected
SSH context. The bucket mount, FUSE process, and containers all run on the VM:

```
┌──────────── App server ────────────┐        ┌─────────────── GCP VM ───────────────┐
│ Node app → createDockerSandbox      │  ssh   │ Docker Engine (daemon)                │
│ @zukhruf/docker (Engine API)         │ ─────▶ │  ├─ rclone plugin (env_auth = true)   │
│ DOCKER_CONTEXT=gcp-vm               │        │  ├─ volume "agent-storage" → gcs:…    │
│ (no daemon here)                    │        │  └─ sandbox containers mount it       │
└─────────────────────────────────────┘        │ Attached service account ──▶ metadata │
                                                │ server ──▶ Google Cloud Storage       │
                                                └───────────────────────────────────────┘
```

> This setup uses an external named volume backed by rclone. A bind mount also
> works with a remote daemon when its `hostPath` exists on the VM: Docker checks
> the path on the daemon host. Files on the app server are not mounted remotely.

### VM setup

#### 1. Let the VM's service account reach the bucket

GCE credentials are read automatically from the metadata server — no key files. Grant the VM's attached service account object access to the bucket:

```bash
gcloud storage buckets add-iam-policy-binding gs://YOUR_BUCKET \
  --member="serviceAccount:VM_SERVICE_ACCOUNT_EMAIL" \
  --role="roles/storage.objectAdmin" \
  --project YOUR_PROJECT
```

The VM also needs an OAuth **access scope** that includes storage. `cloud-platform` is simplest:

```bash
# Changing scopes requires the VM to be stopped first.
gcloud compute instances set-service-account YOUR_VM \
  --service-account VM_SERVICE_ACCOUNT_EMAIL \
  --scopes cloud-platform \
  --zone YOUR_ZONE --project YOUR_PROJECT
```

#### 2. Install the rclone volume plugin

Use the tag matching the VM's architecture (`amd64` or `arm64`):

```bash
docker plugin install rclone/docker-volume-rclone:amd64 \
  args="-v" --alias rclone --grant-all-permissions
```

#### 3. Write the rclone config, then enable

On a GCP VM, `env_auth = true` makes rclone use the attached service account via the metadata server — no credentials in the file. `bucket_policy_only = true` is required for buckets with uniform bucket-level access.

```bash
sudo mkdir -p /var/lib/docker-plugins/rclone/config
sudo tee /var/lib/docker-plugins/rclone/config/rclone.conf >/dev/null <<'EOF'
[gcs]
type = google cloud storage
env_auth = true
bucket_policy_only = true
EOF

docker plugin enable rclone
```

> Enable the plugin **after** the config exists. A managed plugin only re-reads its config on `disable`/`enable`, and once a volume references it you can no longer disable it. Enabling against a missing or invalid config leaves a plugin whose background uploader is dead — reads work, writes silently stay in the local cache and never reach GCS.

#### 4. Create the volume(s)

```bash
docker volume create agent-storage -d rclone \
  -o remote=gcs:YOUR_BUCKET \
  -o vfs-cache-mode=writes \
  -o vfs-write-back=1s
```

The bucket-to-volume mapping is decided here, so both isolation models fall out of how you create volumes — no DeepAgents change:

```bash
# Bucket per agent
docker volume create agent-a -d rclone -o remote=gcs:bucket-a -o vfs-cache-mode=writes
docker volume create agent-b -d rclone -o remote=gcs:bucket-b -o vfs-cache-mode=writes

# One bucket, a prefix per agent
docker volume create agent-a -d rclone -o remote=gcs:shared/agent-a -o vfs-cache-mode=writes
docker volume create agent-b -d rclone -o remote=gcs:shared/agent-b -o vfs-cache-mode=writes
```

### App server setup

#### 5. Point the Docker CLI at the VM

A [docker context](https://docs.docker.com/engine/manage-resources/contexts/) is the cleanest way to target the remote daemon. SSH needs no exposed ports or TLS certs:

```bash
docker context create gcp-vm --docker "host=ssh://USER@VM_HOST"
```

Select it per-process via the environment that runs your app (preferred over `docker context use`, which mutates global state):

```bash
DOCKER_CONTEXT=gcp-vm node your-app.ts
```

DeepAgents reads this context from `process.env` and connects through
`@zukhruf/docker`. Image builds and Compose use the Docker CLI with the same
resolved engine. Keep `DOCKER_HOST` unset when selecting by `DOCKER_CONTEXT`;
the installed client gives `DOCKER_HOST` precedence.

To select an engine for one sandbox, pass
`environment: { ...process.env, DOCKER_CONTEXT: 'gcp-vm' }` to
`createDockerSandbox()`. This leaves the process environment unchanged.

#### 6. Attach the volume

```typescript
import { createDockerSandbox } from '@deepagents/context';

const sandbox = await createDockerSandbox({
  image: 'node:lts-alpine',
  volumes: [
    {
      type: 'volume',
      name: 'agent-storage',
      containerPath: '/workspace/storage',
      readOnly: false,
      lifecycle: 'external', // the volume already exists on the VM; DeepAgents only inspects it
    },
  ],
});

await sandbox.run({ command: 'echo "result" > /workspace/storage/output.txt' });
```

The file written at `/workspace/storage/output.txt` becomes an object in `gcs:YOUR_BUCKET`.

## Same-host daemon: gcsfuse + `gcs()`

When your app process and the Docker daemon run on the **same Linux host**, you can skip the rclone plugin: mount the bucket on the host with [gcsfuse](https://github.com/GoogleCloudPlatform/gcsfuse) and bind that mountpoint in with the `gcs()` helper. The host does all the FUSE work; the sandbox gets a plain bind mount with **no capabilities and no in-container FUSE**.

> `gcs()` returns a bind volume. Its `hostPath` must name the mounted directory
> on the Docker daemon's host; Docker checks that the path exists. This recipe
> mounts the bucket on a Linux daemon host. The app may run on that host or
> connect remotely. For an app on macOS, the remote Linux daemon setup above
> keeps gcsfuse and the bucket mount on the VM.

### On the daemon host

```bash
# 1. Install gcsfuse (Debian/Ubuntu shown; see the gcsfuse docs for other distros)
export GCSFUSE_REPO=gcsfuse-$(lsb_release -c -s)
echo "deb https://packages.cloud.google.com/apt $GCSFUSE_REPO main" \
  | sudo tee /etc/apt/sources.list.d/gcsfuse.list
curl https://packages.cloud.google.com/apt/doc/apt-key.gpg | sudo apt-key add -
sudo apt-get update && sudo apt-get install -y gcsfuse

# 2. Make credentials available to the host (ADC): a service account key, or on GCE the metadata server.
gcloud auth application-default login   # dev; on GCE the attached SA is used automatically

# 3. Mount the bucket as root so the container (any uid) can read it via allow_other.
sudo mkdir -p /mnt/gcs
sudo gcsfuse -o allow_other --implicit-dirs YOUR_BUCKET /mnt/gcs
```

> `allow_other` is what lets a container process — frequently not the mounting user — read the mount. As root (`sudo`) it works directly; if you mount as a non-root user you must first uncomment `user_allow_other` in `/etc/fuse.conf`. Docker bind mounts are recursive, so binding `/mnt/gcs` captures the gcsfuse mount that already lives there (mount the bucket **before** creating the sandbox).

Unmounting is the host's job too: `fusermount -u /mnt/gcs`. The sandbox does not manage the host mount lifecycle. As with rclone, gcsfuse is FUSE over object storage — whole-file create-and-close writes are the reliable pattern, and a freshly written object may take a moment to appear.

### In your app

```typescript
import { createDockerSandbox, gcs } from '@deepagents/context';

const sandbox = await createDockerSandbox({
  volumes: [gcs({ hostPath: '/mnt/gcs', mountPath: '/workspace/storage' })],
});

await sandbox.run({ command: 'echo "result" > /workspace/storage/output.txt' });
```

`gcs()` is a thin constructor that returns an ordinary `DockerBindVolume` over the host mountpoint — it runs no gcsfuse, touches no credentials, and makes no GCS calls. The cloud wiring stays on the host; the sandbox just sees a bind mount.

## Things to know

- **Uploads are asynchronous.** With `vfs-cache-mode=writes`, writes land in a local cache and upload asynchronously after the file closes and the `--vfs-write-back` delay elapses (rclone default `5s`; the volume above uses `1s`), with a final flush on unmount. The upload is async even at `0s`, so a reader on the GCS side must poll for the object or read through the mount. A low `vfs-write-back` costs extra uploads when the same file is re-written rapidly (no coalescing) — fine for whole-file create-and-close writes.
- **Each sandbox selects its own daemon.** By default, `createDockerSandbox()` reads `process.env`. Pass a separate `environment` to each call to target multiple VMs from one app process. Container variables belong in `env`.
- **This is FUSE over object storage.** Tools that do in-place random writes can misbehave; whole-file create-and-close writes are the reliable pattern.
- **No backend logic in the mount path.** The sandbox attaches only ordinary Docker storage primitives (named volumes and bind mounts). `gcs()` is a naming convenience that produces a bind volume — not a special volume type and not a code path that talks to GCS; credentials, gcsfuse, and IAM all live on the host. The same approach works for any backend (S3, Azure, SFTP) by changing the host mount or the rclone `remote`.
