title: Skills
description: Progressive disclosure from an application-owned catalog of SKILL.md files
---

Skills are modular instruction packages that an application makes available to
an agent. The system prompt contains only each skill's name, description, and
model-visible `SKILL.md` path. When a skill applies, the model reads the full
instructions through its file tools.

## Ownership

The application owns both provisioning and discovery:

| Responsibility                                     | Owner                        |
| -------------------------------------------------- | ---------------------------- |
| Put skill files in a filesystem the agent can read | Application                  |
| Discover skills or read a catalog/manifest         | Application                  |
| Construct `AvailableSkill[]`                       | Application                  |
| Render the explicit catalog into context           | `skills()` fragment          |
| Read a selected `SKILL.md` at runtime              | Model through its file tools |

`createBashTool()` does not upload, mount, discover, or expose skills. The
`skills()` fragment does not inspect a sandbox or filesystem. This keeps the
context layer independent from local directories, GCS, container volumes, and
provider-specific upload APIs.

## AvailableSkill

The caller describes each available skill with one model-facing type:

```typescript
interface AvailableSkill {
  name: string;
  description: string;
  /** Path to SKILL.md as seen by the model's file tools. */
  path: string;
}
```

`path` is the runtime-visible file path, not a host-side source path. For
example, if a GCS-backed volume is mounted at `/skills`, the catalog might be:

```typescript
import type { AvailableSkill } from '@deepagents/context';

const availableSkills: AvailableSkill[] = [
  {
    name: 'deploy',
    description: 'Deploy services with safe rollout checks.',
    path: '/skills/deploy/SKILL.md',
  },
  {
    name: 'data-analysis',
    description: 'Analyze datasets and summarize findings.',
    path: '/skills/data-analysis/SKILL.md',
  },
];
```

GCS is storage, not an implicit skills registry. Your application can build
this array from a GCS manifest, a database, configuration, or its own scan of
the mounted filesystem. The context package does not choose one of those
sources.

## Provision the Files

Provisioning happens before the fragment is created. A container application
can mount a volume when it creates the sandbox backend:

```typescript
const backend = await createDockerSandbox({
  volumes: [
    {
      type: 'bind',
      hostPath: '/mnt/gcs/agent-skills',
      containerPath: '/skills',
      readOnly: true,
    },
  ],
});

const sandbox = await createBashTool({ sandbox: backend });
```

The same boundary applies to other runtimes: the application may use a native
volume, image layer, remote sandbox API, or a generic file-copy step. Whatever
mechanism it uses must make every supplied `AvailableSkill.path` readable by
the model's tools.

## Add the Catalog to Context

Pass the explicit array to `skills()`:

```typescript
import {
  ContextEngine,
  InMemoryContextStore,
  role,
  skills,
} from '@deepagents/context';

const context = new ContextEngine({
  store: new InMemoryContextStore(),
  chatId: 'chat-001',
  userId: 'user-001',
}).set(role('You are a helpful assistant.'), skills(availableSkills));
```

The fragment renders Codex's skills catalog as written, in every renderer:

```text
<skills_instructions>
## Skills
A skill is a set of instructions provided through a `SKILL.md` source. ...
### Available skills
- deploy: Deploy services to production. (file: /skills/deploy/SKILL.md)
### How to use skills
- Discovery: The list above is the skills available in this session ...
...
</skills_instructions>
```

Each supplied item becomes one `- name: description (file: path)` line, or
`- name: (file: path)` when its description is empty. With no skills the
fragment renders nothing. Like every `verbatim()` fragment, it renders only at
the top level of a context: pass it to `set()`, not inside another fragment.

It does not check that paths exist. File accessibility remains the
application's responsibility.

### Limits

The lines follow Codex's rules for host skill files:

- Lines are ordered by name, then path, in code-unit order (`'Zeta'` before
  `'alpha'`), not in the order supplied.
- A description longer than 1024 characters is cut to its first 1021 and
  `...`. Characters are Unicode code points, so an emoji counts as one.
- All skill lines share a budget of 8000 characters, each line costing its
  length plus one for its newline. The intro and the how-to text are not
  counted. When the full lines exceed it, every line keeps its name and path
  and the rest of the budget is shared over the descriptions one character at
  a time, round-robin. When even the bare lines exceed it, every description
  is dropped and skills past the budget are left out.

When skills are left out, the fragment's `metadata.warning` holds Codex's
warning:

```typescript
const fragment = skills(manySkills);
fragment.metadata.warning;
// 'Exceeded skills context budget. All skill descriptions were removed and
//  58 additional skills were not included in the model-visible skills list.'
```

`metadata.warning` is absent when every skill is listed.
`getAvailableSkills()` still returns every supplied skill, uncut and in the
order supplied.

## Read the Catalog from Context

`ContextEngine.getAvailableSkills()` returns the catalog stored by the first
`skills()` fragment:

```typescript
const catalog = context.getAvailableSkills();
// [{ name: 'deploy', description: '...', path: '/skills/deploy/SKILL.md' }]
```

The agent uses this same catalog for `GuardrailContext.availableSkills`, so a
guardrail that corrects skill/tool confusion refers to the exact path shown to
the model.

## Parse Frontmatter Content

`parseFrontmatter()` remains available as a host-neutral utility. It parses a
string that your application has already read; it does not read a path or
discover directories.

```typescript
import { parseFrontmatter } from '@deepagents/context';

const source = `---
name: deploy
description: Deploy services safely
---

## Workflow
1. Validate
2. Roll out`;

const { frontmatter, body } = parseFrontmatter(source);
```

Your discovery code can combine the parsed `name` and `description` with the
runtime path it assigned to build an `AvailableSkill`.

`parseSkillFrontmatter(content, defaultName)` parses a `SKILL.md` as Codex's
skill loader does and returns `{ name, description }`:

```typescript
import { SkillParseError, parseSkillFrontmatter } from '@deepagents/context';

const { name, description } = parseSkillFrontmatter(source, 'deploy');
```

- The name and description are collapsed to one line.
- A missing or empty name becomes `defaultName`, such as the skill's
  directory name. The name does not have to match the directory.
- A file it rejects throws a `SkillParseError` with Codex's error text:
  `missing YAML frontmatter delimited by ---`, `invalid YAML: …`,
  ``missing field `description` `` or
  `invalid name: exceeds maximum length of 64 characters`.

## Explicit Skill Mentions

A user who names a skill as `$deploy`, or links it as
`[$deploy](/skills/deploy/SKILL.md)`, asks for that skill. Codex then injects
the whole `SKILL.md` after the user's message. Three exports follow Codex's
rules for that:

```typescript
import {
  collectExplicitSkillMentions,
  extractToolMentions,
  skillInstructions,
} from '@deepagents/context';

const selected = collectExplicitSkillMentions(
  ['use $deploy, then $lint'],
  availableSkills,
);
const text = skillInstructions({
  name: selected[0].name,
  path: selected[0].path,
  contents: skillMd,
});
// '<skill>\n<name>deploy</name>\n<path>/skills/deploy/SKILL.md</path>\n---\nname: deploy\n…\n</skill>'
```

- `extractToolMentions(text)` returns the `names`, linked `paths` and
  `plainNames` of one text. A name is `[A-Za-z0-9_:-]+` after `$`. A link with
  an empty path counts as a plain `$name`. `$PATH`, `$HOME`, `$USER`,
  `$SHELL`, `$PWD`, `$TMPDIR`, `$TEMP`, `$TMP`, `$LANG`, `$TERM` and
  `$XDG_CONFIG_HOME` are dropped in any case. Code spans are read like any
  other text.
- `collectExplicitSkillMentions(inputs, skills)` scans each input in turn: its
  linked paths select first (a `skill://` prefix is ignored), then its plain
  names, both in the order of `skills`. A skill is selected once. A plain name
  that more than one skill uses selects none of them, and an unknown name is
  ignored.
- `skillInstructions({ name, path, contents })` builds Codex's `<skill>`
  block. `contents` is the whole `SKILL.md`, frontmatter included.

Reading the files and placing the messages belong to the application.

## Skill Reminders

The baseline `skills()` fragment lists the entire explicit catalog.
`skillsReminder()` is separate: it ranks the same `AvailableSkill[]` against a
user message and repeats the most relevant entries as a reminder. See
[Skill Reminders](/docs/context/skill-reminders).

## Provider-Native Skills

AI providers may offer APIs that upload file content into a provider-managed
skill store. That is a separate deployment model. Files already exposed to an
agent through a mounted volume do not need to be uploaded by this fragment or
by `createBashTool()`.
