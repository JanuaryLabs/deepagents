This page explains the internal architecture of the sandbox system. Read this if you want to understand how the pieces fit together, extend the system with a custom engine or strategy, or debug issues.

## Engine bridge + strategies

Docker and Apple Container share creation strategies. Each backend supplies
an engine that handles its container runtime:

- **Bridge (dialect axis).** `ContainerEngine<TOpts>` defines how to attach to
  a named container, start a container, inspect and manage volumes, build an
  image, and release the engine connection. It returns an `EngineContainer`
  that executes commands, streams processes, reads and writes files, provides
  an installer context, and stops the container. There is one engine per
  backend: `DockerEngine` uses the Engine API through `@zukhruf/docker`, and
  `appleEngine` uses the `container` CLI.
- **Template Method (mode axis).** A single `ContainerSandboxStrategy<TOpts>`
  owns the shared lifecycle (resolve an image, prepare volumes, start a
  long-running container, configure it, then return the common sandbox methods)
  and delegates every engine operation to its injected engine. It is typed to
  `CommonSandboxOptions`, so the skeleton can never read an engine-only knob
  (Docker's security/network; Apple's `arch`). Subclasses pick the _mode_.

```
ContainerEngine<TOpts>            ← dialect seam (one impl per backend)
├── DockerEngine                  — Engine API (@zukhruf/docker); CLI only for builds and Compose
└── appleEngine                   — container CLI (per-container VMs, virtiofs)

ContainerSandboxStrategy<TOpts>   ← shared skeleton, engine-injected
├── RuntimeStrategy               — install packages/binaries at runtime
└── ContainerfileStrategy         — build image from a Dockerfile (cached)

ComposeStrategy                   — Docker-only subclass; overrides stack acquisition and release
```

### Template method flow

The base strategy defines the creation algorithm and delegates each engine
operation to the engine or container. Runtime and Dockerfile strategies
override `getImage()` and `configure()`; Compose also overrides acquisition
and release:

```
create()
  │
  ├─ 1. getImage()           ← mode-specific
  │     ├─ Runtime:       return image name (or engine.defaultImage)
  │     ├─ Containerfile:  engine.buildImage(...) if needed, return cached tag
  │     └─ Compose:       return '' (compose manages images)
  │
  ├─ 2. acquireContainer()   ← common: engine.attach(name) for a named sandbox,
  │     │                       else prepareVolumes() and engine.run(...)
  │     └─ Compose override:  docker compose up -d, then find the service container
  │
  ├─ 3. engine.ensureWorkdir()  ← new containers only; no-op on Docker, `mkdir -p` on Apple
  │
  ├─ 4. configure()          ← new containers only, mode-specific
  │     ├─ Runtime:       run installers via container.installerContext()
  │     ├─ Containerfile:  no-op (image already configured)
  │     └─ Compose:       no-op (compose file defines everything)
  │
  ├─ 5. assertBashAvailable()   ← new and attached containers
  │
  ├─ 6. createSandboxMethods()  ← command, process, file, and disposal methods
  │
  └─ 7. readiness(sandbox)      ← optional caller hook, awaited before return
```

If setup fails, the base class releases a newly acquired container, removes
managed volumes it created, and disposes the engine. An attached container is
left running when setup fails. If the readiness hook fails, the
sandbox is disposed, including an attached container.

The methods object returned by `createSandboxMethods()` also implements
`[Symbol.asyncDispose]`, which delegates to `dispose()`. Because
`DisposableSandbox extends AsyncDisposable`, callers can bind any backend with
`await using` and the container is torn down at scope exit.

### Container startup

All single-container strategies start a long-running container and then execute
commands inside it. Docker sends the create request of the Engine API with the
body that `docker run -d --rm` sends for the same options. A named sandbox uses
`containers.createOrGet()`, so the container that exists wins. When the image
is missing, the engine pulls it and creates the container again. Apple
Container uses `container run` with equivalent name, resource, volume,
environment, arch, and command controls where the Apple CLI supports them.

Command resolution for Runtime and Dockerfile strategies:

- `command` omitted (default): append `tail -f /dev/null` as a keep-alive.
- `command: null` or `command: []`: append nothing; image/Dockerfile
  `CMD`/`ENTRYPOINT` run as declared.
- Non-empty `command`: append verbatim, overriding image/Dockerfile `CMD`.

Commands then run through the exec requests of the Engine API, as
`bash -lc "<command>"`.

Apple Container follows the same shape with `container run --detach --rm ...`
and executes commands via `container exec <id> bash -lc "<command>"`. It does not
support Compose, Docker volume drivers, or Docker security/network flags;
instead each container runs inside its own lightweight VM and exposes a smaller
set of resource, arch, bind-mount, named-volume, and environment controls.

### Dockerfile image caching

The shared `ContainerfileStrategy` generates a deterministic image tag from the
Dockerfile content plus the build `identity` (Docker's `platform` / Apple's
`arch`), then asks the engine to build only on a cache miss:

```
Dockerfile content + identity → SHA-256 → first 12 chars → "sandbox-a1b2c3d4e5f6"
```

Same Dockerfile + identity produces the same tag. The strategy checks
`engine.imageExists(tag)` and calls `engine.buildImage(...)` only when it is
missing; Docker's layer cache handles `docker build`, and Apple Container skips
`container build` when the tag already exists locally.

### Compose overrides

`ComposeStrategy` overrides two base class methods:

| Method               | Standard           | Compose Override                                                         |
| -------------------- | ------------------ | ------------------------------------------------------------------------ |
| `acquireContainer()` | `engine.run(...)`  | `docker compose up -d`, then the service container by its Compose labels |
| `release()`          | `container.stop()` | `docker compose down`                                                    |

Commands and file operations use the service container's Engine API handle.

## Binary bridges

Binary bridges connect just-bash virtual environments to real host binaries. They solve three path resolution problems:

### Virtual CWD to real CWD

just-bash uses virtual paths like `/home/user`. Binary bridges resolve them to real host paths:

```
ReadWriteFs:  root + cwd → path.join(fs.root, ctx.cwd)
OverlayFs:    fs.toRealPath(ctx.cwd)
InMemoryFs:   fallback to process.cwd()
```

### Virtual PATH to real PATH

just-bash sets `PATH=/bin:/usr/bin` which doesn't include host binary locations (nvm, homebrew, etc.). Binary bridges always use `process.env.PATH` for binary resolution.

### File argument detection

Arguments that look like file paths are resolved relative to the real CWD:

```
Detected as path:     Has file extension (.md, .py), contains /, starts with .
Passed through:       Starts with - (flags), no path indicators
```

### Security via allowedArgs

```typescript
createBinaryBridges({
  name: 'git',
  allowedArgs: /^(status|log|diff|show)/,
});

// Allowed:  git status, git log, git diff
// Blocked:  git log --oneline (flags are also tested), git reset --hard
```

Each argument is tested individually against the regex. Any non-matching argument returns exit code 1 with a security policy error.

## Integration pipeline

To give an AI agent a bash tool that runs inside a sandbox, compose the two
independent systems explicitly at the call site:

```
1. createDockerSandbox(sandboxOptions)
   └─ Returns: DisposableSandbox (the AI SDK sandbox session, plus dispose)

2. createBashTool({ sandbox, ...bashOptions })
   └─ Returns: { bash, tools, sandbox }
```

Skill provisioning and discovery are application concerns. After making files
available through the backend, pass explicit `AvailableSkill[]` metadata to the
`skills()` context fragment; `createBashTool` does not inspect those files.

Any `DisposableSandbox` matches what `createBashTool` expects from its
`sandbox` parameter: `run({ command, workingDirectory, env, abortSignal }) →
{ stdout, stderr, exitCode }`. `spawn` streams stdout and stderr while the process
runs. Microsandbox and Daytona still use the older contract, and `createBashTool`
adapts them. The bash tool forwards the AI SDK's `executionOptions.abortSignal`
to `run` as `abortSignal`.

### File operations

Docker moves files through the archive requests of the Engine API
(`readFile()`, `writeFiles()`, `stat()`). These requests cannot reach a tmpfs
mount, `/proc`, `/sys` or `/dev`. For a path there, Docker uses an exec: a script
for a read or a `stat`, and `cat` with the bytes on standard input for a write.
A read and a `stat` follow symbolic links. Files and new parent directories belong to the
container user selected by `security.user` or the image's `USER`. Names and
numeric IDs are supported; names are resolved inside the container.

Apple Container moves files through `container exec`, because its CLI has no
file requests: the bytes go to standard input for a write, and come back as
base64 for a read. `listDirectory` and `deleteFile` use a script on
both engines, because the engines have no request for them.

Await `spawn()` to receive a process with two byte streams (`stdout`, `stderr`),
`wait()` and `kill()`. No engine has a request that stops an exec, so each
process runs under a small wrapper. The wrapper records the process group, and
`kill()` and an abort kill that group from a second exec.

## Extending

There are two extension points, one per axis:

**Add a backend → implement `ContainerEngine`.** Provide the engine
operations (attach, run, volumes, image build, dispose) and an
`EngineContainer` for each container (commands, processes, files, installer
context, stop). Then write a factory that passes the engine to the shared
strategies. No strategy subclass is necessary. `appleEngine` works this way.

```typescript
import {
  type CommonSandboxOptions,
  type ContainerEngine,
  ContainerfileStrategy,
  RuntimeStrategy,
} from '@deepagents/context';

const podmanEngine: ContainerEngine = {
  attach: async (name, image) => {
    /* the running container, or undefined */
  },
  run: async (image, name, opts, workdir) => {
    /* { created, container } */
  },
  // volumeExists, createVolume, removeVolume, ensureWorkdir, imageExists,
  // buildImage, dispose, errors, ... (the full engine seam)
};

export function createPodmanSandbox(options: CommonSandboxOptions = {}) {
  return new RuntimeStrategy(options, podmanEngine, {
    image: options.image ?? podmanEngine.defaultImage,
    installers: options.installers ?? [],
  }).create();
}
```

**Add a creation mode → subclass `ContainerSandboxStrategy`.** Override
`getImage()` / `configure()` (and any lifecycle method, as `ComposeStrategy`
does) while it still delegates each engine operation to the injected engine.
