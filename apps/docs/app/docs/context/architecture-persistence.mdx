The persistence layer stores conversation graphs across SQLite, PostgreSQL, and
SQL Server. Each adapter implements the `ContextStore` abstract class.

## ContextStore abstract class

### Interface overview

`ContextStore` groups its methods into six categories:

```typescript
abstract class ContextStore {
  // Chat operations
  abstract createChat(chat: ChatData): Promise<StoredChatData>;
  abstract upsertChat(chat: ChatData): Promise<StoredChatData>;
  abstract getChat(chatId: string): Promise<StoredChatData | undefined>;
  abstract updateChat(
    chatId: string,
    update: ChatUpdater,
  ): Promise<StoredChatData>;
  abstract listChats(options?: ListChatsOptions): Promise<ChatInfo[]>;
  abstract deleteChat(
    chatId: string,
    options?: DeleteChatOptions,
  ): Promise<boolean>;

  // Message operations
  abstract addMessage(message: MessageData): Promise<void>;
  async addMessages(messages: MessageData[]): Promise<void> {
    for (const message of messages) {
      await this.addMessage(message);
    }
  }
  abstract getMessage(messageId: string): Promise<MessageData | undefined>;
  abstract getMessageChain(headId: string): Promise<MessageData[]>;
  abstract getMessages(chatId: string): Promise<MessageData[]>;
  abstract hasChildren(messageId: string): Promise<boolean>;
  abstract setMessageParent(
    messageId: string,
    parentId: string | null,
  ): Promise<void>;

  // Branch operations
  abstract createBranch(branch: BranchData): Promise<void>;
  abstract getBranch(
    chatId: string,
    name: string,
  ): Promise<BranchData | undefined>;
  abstract getActiveBranch(chatId: string): Promise<BranchData | undefined>;
  abstract setActiveBranch(chatId: string, branchId: string): Promise<void>;
  abstract updateBranchHead(
    branchId: string,
    messageId: string | null,
    expectedHeadMessageId: string | null,
  ): Promise<boolean>;
  abstract listBranches(chatId: string): Promise<BranchInfo[]>;

  // Checkpoint operations
  abstract createCheckpoint(checkpoint: CheckpointData): Promise<void>;
  abstract getCheckpoint(
    chatId: string,
    name: string,
  ): Promise<CheckpointData | undefined>;
  abstract listCheckpoints(chatId: string): Promise<CheckpointInfo[]>;
  abstract deleteCheckpoint(chatId: string, name: string): Promise<void>;

  // Search operations
  abstract searchMessages(
    chatId: string,
    query: string,
    options?: SearchOptions,
  ): Promise<SearchResult[]>;

  // Visualization operations
  abstract getGraph(chatId: string): Promise<GraphData>;
}
```

`updateChat` calls an updater with the stored chat while holding the store's
write lock. Return changes to `title` or `metadata`, or `undefined` to leave the
chat unchanged.

`updateBranchHead` compares the stored head with `expectedHeadMessageId` before
advancing it. It returns `true` on success and `false` if another writer changed
the head. Re-read and reconcile after a conflict. The save pipeline uses
`setMessageParent` to graft a competing turn onto the current head before retrying.

The default `addMessages` calls `addMessage` sequentially. The SQLite adapter
overrides it to persist each batch in a transaction.

**Source:** `packages/context/src/lib/store/store.ts` and
`packages/context/src/lib/save/save-pipeline.ts`.

### Method categories

| Category      | Methods | Purpose                                                 |
| ------------- | ------- | ------------------------------------------------------- |
| Chat          | 6       | Container lifecycle: create, read, update, delete, list |
| Message       | 7       | Graph nodes: add, batch, retrieve, traverse, re-parent  |
| Branch        | 6       | Pointers: create, switch, update head                   |
| Checkpoint    | 4       | Bookmarks: create, retrieve, delete                     |
| Search        | 1       | Full-text search across messages                        |
| Visualization | 1       | Export complete graph for debugging                     |

## SQLite adapter

The `SqliteContextStore` uses the built-in `node:sqlite` module in Node.js 24.9.0
or later for local persistence.

### Initialization

```typescript
import { Declaration } from '@zukhruf/sqlite-drift';
import { open } from '@zukhruf/sqlite-open';
import type { DatabaseSync, SQLTagStore } from 'node:sqlite';

import { SETUP, searchStatements, statements } from './ddl.sqlite.ts';

const tables = new Declaration(statements, { rows: 'keep' });
const search = new Declaration(searchStatements, { rows: 'replace' });

class SqliteContextStore extends ContextStore {
  #db: DatabaseSync;
  #sql: SQLTagStore;

  constructor(pathOrDb: string | DatabaseSync) {
    super();
    this.#db = typeof pathOrDb === 'string' ? open(pathOrDb) : pathOrDb;
    this.#db.exec(SETUP);
    tables.apply(this.#db);
    search.apply(this.#db);
    this.#sql = this.#db.createTagStore();
  }
}
```

**Source:** `SqliteContextStore` in `packages/context/src/lib/store/sqlite.store.ts`.

### Statement caching

`DatabaseSync.createTagStore()` supplies the store's prepared statement cache.
Tagged queries bind interpolated values as parameters:

```typescript
this.#sql.run`DELETE FROM messages_fts WHERE messageId = ${message.id}`;
this.#sql.run`INSERT INTO messages_fts(messageId, chatId, name, content)
   VALUES (${message.id}, ${message.chatId}, ${message.name}, ${content})`;
```

Repeated tagged queries reuse prepared statements. Dynamic SQL, including
`searchMessages` queries with optional role filters, still uses `prepare()`
directly.

**Source:** `#insertMessage` and `searchMessages` in `packages/context/src/lib/store/sqlite.store.ts`.

### Recursive CTE for message chain

SQLite's recursive CTE walks the parent chain:

```sql
WITH RECURSIVE chain AS (
  SELECT *, 0 as depth FROM messages WHERE id = ?
  UNION ALL
  SELECT m.*, c.depth + 1 FROM messages m
  INNER JOIN chain c ON m.id = c.parentId
  WHERE c.depth < 100000
)
SELECT * FROM chain
ORDER BY depth DESC
```

**Source:** `getMessageChain` in `packages/context/src/lib/store/sqlite.store.ts`.

### Transaction handling

Multi-step SQLite writes use `transaction` from `@zukhruf/sqlite-transaction` to commit on
success and roll back on failure. For example, a message batch uses a deferred
transaction:

```typescript
import { transaction } from '@zukhruf/sqlite-transaction';

transaction(
  this.#db,
  () => {
    for (const message of messages) {
      this.#insertMessage(message);
    }
  },
  { mode: 'deferred' },
);
```

Read-modify-write operations such as `updateChat` use `mode: 'immediate'` to
acquire the write lock before reading the current value.

**Source:** `addMessages` and `updateChat` in `packages/context/src/lib/store/sqlite.store.ts`.

## PostgreSQL adapter

The `PostgresContextStore` uses the `pg` package for PostgreSQL persistence.

### Pool-based connections

Pass a connection string, `PoolConfig` object, or existing `pg.Pool` instance as
`options.pool`. Open the store with `await PostgresContextStore.create(options)`;
it initializes the schema before returning.

```typescript
import type { Pool, PoolConfig } from 'pg';

import { lockSchemaDDL } from '@deepagents/context';

class PostgresContextStore extends ContextStore {
  #pool: Pool;
  #schema: string;
  #ownsPool: boolean;

  private constructor(options: PostgresStoreOptions) {
    super();
    const schema = options.schema ?? 'public';
    this.#schema = schema;
    const pg = PostgresContextStore.#requirePg();
    if (options.pool instanceof pg.Pool) {
      this.#pool = options.pool;
      this.#ownsPool = false;
    } else {
      this.#pool =
        typeof options.pool === 'string'
          ? new pg.Pool({ connectionString: options.pool })
          : new pg.Pool(options.pool);
      this.#ownsPool = true;
    }
  }

  static async create(
    options: PostgresStoreOptions,
  ): Promise<PostgresContextStore> {
    const store = new PostgresContextStore(options);
    try {
      await store.#initialize();
    } catch (error) {
      await store.close();
      throw error;
    }
    return store;
  }

  async #initialize(): Promise<void> {
    await this.#pool.query(lockSchemaDDL(storeDDL(this.#schema), this.#schema));
  }
}
```

The `schema` option scopes the store's tables and indexes to a PostgreSQL schema.
It defaults to `'public'`.

`lockSchemaDDL` prefixes the DDL with a transaction-scoped PostgreSQL advisory
lock keyed by the schema. The store sends both as one parameterless query, so
concurrent initializations of the same schema run one at a time. The lock is
released when that transaction commits or rolls back.

When an existing `Pool` is passed, `close()` does not end the pool (the caller retains ownership). When the store creates its own pool, `close()` ends it.

**Source:** `#initialize` in `packages/context/src/lib/store/postgres.store.ts` and `packages/context/src/lib/store/postgres-schema-lock.ts`.

### JSONB for metadata

PostgreSQL stores metadata as JSONB:

```sql
CREATE TABLE chats (
  id TEXT PRIMARY KEY,
  "userId" TEXT NOT NULL,
  title TEXT,
  metadata JSONB,
  "createdAt" BIGINT NOT NULL DEFAULT EXTRACT(EPOCH FROM NOW()) * 1000,
  "updatedAt" BIGINT NOT NULL DEFAULT EXTRACT(EPOCH FROM NOW()) * 1000
);
```

### tsvector + GIN for full-text search

PostgreSQL uses `tsvector` columns with GIN indexes:

```sql
CREATE TABLE messages_fts (
  "messageId" TEXT PRIMARY KEY REFERENCES messages(id) ON DELETE CASCADE,
  "chatId" TEXT NOT NULL,
  name TEXT NOT NULL,
  content_vector TSVECTOR NOT NULL
);

CREATE INDEX idx_messages_fts_vector ON messages_fts USING GIN(content_vector);
```

**Search query:**

```sql
SELECT m.*, ts_rank(f.content_vector, plainto_tsquery($2)) as rank
FROM messages_fts f
JOIN messages m ON m.id = f."messageId"
WHERE f."chatId" = $1
  AND f.content_vector @@ plainto_tsquery($2)
ORDER BY rank DESC
LIMIT $3
```

### Async transaction handling

PostgreSQL uses client-based transactions.

```typescript
async #useTransaction<T>(fn: (client: PoolClient) => Promise<T>): Promise<T> {
  const client = await this.#pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (error) {
    await client.query('ROLLBACK');
    throw error;
  } finally {
    client.release();
  }
}
```

**Source:** `#useTransaction` in `packages/context/src/lib/store/postgres.store.ts`.

## SQL Server adapter

The `SqlServerContextStore` uses the `mssql` package. Its search queries use
full-text search when installed and `LIKE` otherwise.

### Graceful FTS degradation

Each `searchMessages` call checks whether full-text search is installed:

```sql
SELECT CAST(SERVERPROPERTY('IsFullTextInstalled') AS INT) as ftsInstalled
```

If the result is `1`, the store searches with `CONTAINSTABLE`; otherwise it uses
`LIKE`. Errors from the check or search propagate to the caller.

**Source:** `searchMessages` in `packages/context/src/lib/store/sqlserver.store.ts`.

## Schema design

### Text IDs

All IDs use TEXT/VARCHAR instead of integers:

```sql
id TEXT PRIMARY KEY
```

**Why text IDs?**

- UUIDs generated client-side (no round-trip)
- Distributed generation without coordination
- Human-readable in debugging

### BIGINT timestamps

Timestamps store milliseconds since the Unix epoch. SQLite uses `INTEGER`;
PostgreSQL and SQL Server use `BIGINT`:

```sql
createdAt INTEGER NOT NULL DEFAULT (strftime('%s', 'now') * 1000)
```

**Why BIGINT milliseconds?**

- JavaScript-native (Date.now())
- No timezone issues
- Consistent across databases

### CASCADE deletes

Foreign keys use CASCADE for cleanup:

```sql
FOREIGN KEY (chatId) REFERENCES chats(id) ON DELETE CASCADE
```

**Cascade chain:**

```
DELETE FROM chats WHERE id = ?
  → Deletes all messages (chatId FK)
  → Deletes all branches (chatId FK)
  → Deletes all checkpoints (chatId FK)
  → FTS entries cleaned separately
```

### Complete SQLite schema

The schema module defines one `CREATE` statement per object. On each open, the
store runs the connection PRAGMAs, then applies two `@zukhruf/sqlite-drift`
declarations. The main tables use `rows: 'keep'` to preserve their rows during
schema updates. The search table uses `rows: 'replace'`: if its schema changes,
`messages_fts` is recreated empty. Stored messages remain available through history
APIs, but the store does not automatically repopulate the search table from them.

`node:sqlite` enables foreign keys by default, so the store does not set a
foreign-key PRAGMA.

`open` of `@zukhruf/sqlite-open` sets the write-ahead log and a 5 s busy
timeout, so the PRAGMAs do not set them. A connection that you pass in gets
the same settings when `open` made it.

```sql
-- Performance PRAGMAs
PRAGMA synchronous = NORMAL;
PRAGMA cache_size = -64000;
PRAGMA temp_store = MEMORY;
PRAGMA mmap_size = 268435456;

-- Chats table
CREATE TABLE chats (
  id TEXT PRIMARY KEY,
  userId TEXT NOT NULL,
  title TEXT,
  metadata TEXT,
  createdAt INTEGER NOT NULL DEFAULT (strftime('%s', 'now') * 1000),
  updatedAt INTEGER NOT NULL DEFAULT (strftime('%s', 'now') * 1000)
);

CREATE INDEX idx_chats_updatedAt ON chats(updatedAt);
CREATE INDEX idx_chats_userId ON chats(userId);
CREATE INDEX idx_chats_userId_updatedAt ON chats(userId, updatedAt DESC);

-- Messages table (DAG nodes)
CREATE TABLE messages (
  id TEXT PRIMARY KEY,
  chatId TEXT NOT NULL,
  parentId TEXT,
  name TEXT NOT NULL,
  type TEXT,
  data TEXT NOT NULL,
  createdAt INTEGER NOT NULL,
  FOREIGN KEY (chatId) REFERENCES chats(id) ON DELETE CASCADE,
  FOREIGN KEY (parentId) REFERENCES messages(id)
);

CREATE INDEX idx_messages_chatId ON messages(chatId);
CREATE INDEX idx_messages_parentId ON messages(parentId);
CREATE INDEX idx_messages_chatId_parentId ON messages(chatId, parentId);

-- Branches table (pointers)
CREATE TABLE branches (
  id TEXT PRIMARY KEY,
  chatId TEXT NOT NULL,
  name TEXT NOT NULL,
  headMessageId TEXT,
  isActive INTEGER NOT NULL DEFAULT 0,
  createdAt INTEGER NOT NULL,
  FOREIGN KEY (chatId) REFERENCES chats(id) ON DELETE CASCADE,
  FOREIGN KEY (headMessageId) REFERENCES messages(id),
  UNIQUE(chatId, name)
);

CREATE INDEX idx_branches_chatId ON branches(chatId);
CREATE INDEX idx_branches_chatId_isActive ON branches(chatId, isActive);
CREATE INDEX idx_branches_headMessageId ON branches(headMessageId);

-- Checkpoints table (bookmarks)
CREATE TABLE checkpoints (
  id TEXT PRIMARY KEY,
  chatId TEXT NOT NULL,
  name TEXT NOT NULL,
  messageId TEXT NOT NULL,
  createdAt INTEGER NOT NULL,
  FOREIGN KEY (chatId) REFERENCES chats(id) ON DELETE CASCADE,
  FOREIGN KEY (messageId) REFERENCES messages(id),
  UNIQUE(chatId, name)
);

CREATE INDEX idx_checkpoints_chatId ON checkpoints(chatId);
CREATE INDEX idx_checkpoints_messageId ON checkpoints(messageId);

-- FTS5 for full-text search
CREATE VIRTUAL TABLE messages_fts USING fts5(
  messageId UNINDEXED,
  chatId UNINDEXED,
  name UNINDEXED,
  content,
  tokenize='porter unicode61'
);
```

**Source:** `packages/context/src/lib/store/ddl.sqlite.ts` and `packages/context/src/lib/store/sqlite.store.ts`.

### Index strategy

| Index                          | Purpose                                   |
| ------------------------------ | ----------------------------------------- |
| `idx_chats_userId_updatedAt`   | Fast `listChats()` with userId filter     |
| `idx_messages_chatId_parentId` | Fast recursive CTE traversal              |
| `idx_branches_chatId_isActive` | Fast `getActiveBranch()`                  |
| `idx_branches_headMessageId`   | Foreign-key checks when deleting messages |
| `idx_checkpoints_chatId`       | Fast checkpoint listing                   |
| `idx_checkpoints_messageId`    | Foreign-key checks when deleting messages |

## Adapter comparison

| Feature        | SQLite          | PostgreSQL                         | SQL Server                      |
| -------------- | --------------- | ---------------------------------- | ------------------------------- |
| Use case       | Local/embedded  | Production                         | Enterprise                      |
| FTS            | FTS5 (built-in) | tsvector + GIN                     | Optional catalog                |
| JSON           | TEXT            | JSONB                              | NVARCHAR                        |
| Timestamps     | INTEGER         | BIGINT                             | BIGINT                          |
| Connection     | Single file     | Pool                               | Pool                            |
| Schema support | N/A             | `schema` option (default `public`) | `schema` option (default `dbo`) |
| Opening        | Constructor     | `await create()`                   | `await create()`                |
| Dependency     | `node:sqlite`   | `pg`                               | `mssql`                         |
