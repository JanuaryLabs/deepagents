The sandbox system lets AI agents execute real commands in isolated
environments. Choose between Docker containers for portable full binary
execution, Apple Container lightweight VMs for stronger local isolation on
Apple silicon, Microsandbox microVMs for local hardware-isolated OCI images,
Daytona v2 sandboxes for managed remote workspaces, virtual file
systems for simulation, custom `DisposableSandbox` implementations for specialized
policy, or binary bridges to combine approaches.

## When to use what

| Approach                                                                             | Use Case                                                                          | Requires Docker? |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------- | ---------------- |
| `createDockerSandbox` + `createBashTool`                                             | Agent needs real binaries in isolated container                                   | Yes              |
| `createDockerSandbox`                                                                | Direct container control without AI agent wiring                                  | Yes              |
| `createAppleContainerSandbox` + `createBashTool`                                     | Agent needs real binaries in Apple Container lightweight VMs                      | No               |
| `createAppleContainerSandbox`                                                        | Direct VM-backed container control on Apple silicon/macOS 26+                     | No               |
| [`createMicrosandboxSandbox`](/docs/context/microsandbox-sandbox) + `createBashTool` | Agent needs OCI images in local microVMs with streaming process output            | No               |
| `createMicrosandboxSandbox`                                                          | Direct local microVM control; each sandbox is a one-off microVM                   | No               |
| `createDaytonaSandbox(daytona.v2, options)` + `createBashTool`                       | Managed remote sandbox on Daytona v2                                              | No               |
| `createVirtualSandbox`                                                               | In-process bash with a virtual filesystem and optional JavaScript command support | No               |
| `createBinaryBridges`                                                                | Bridge specific host binaries into just-bash virtual FS                           | No               |

All AI-agent-facing surfaces compose the same way: pick a backend factory
(`createDockerSandbox` / `createAppleContainerSandbox` /
`createMicrosandboxSandbox` / `createDaytonaSandbox` /
`createVirtualSandbox`), then wrap it with
`createBashTool({ sandbox })` to get the bash tool and file tools. Skill
provisioning and discovery remain the application's responsibility. For
per-command file-change tracking, first decorate a real backend
with `withStraceFileChanges(...)`, then pass that tracked backend into
`createBashTool`.

`createBashTool` creates its working directory and uploads `files` and
`uploadDirectory` through the sandbox that you give it. With a tracked backend,
`onFileChanges` sees that setup, and a callback that throws makes `createBashTool`
reject. A callback that must not see the setup adds those paths to `exclude`, for
example the working directory itself:

```typescript
const tracked = await withStraceFileChanges(backend, {
  include: ['/workspace', '/workspace/**'],
  exclude: ['/workspace'],
  onFileChanges: rejectForbiddenChanges,
});
```

Uploaded files need their own `exclude` patterns, because `/workspace` matches only
the directory.

`deleteFile` reports a `delete` change when it returns `true`. It reports nothing
when it returns `false` or rejects.

`uploadDirectory` accepts one `{ source, include? }` object. Set the top-level
`workingDirectory` to choose where its files are uploaded and where bash commands run.
Without it, commands run in the sandbox's default working directory, and relative
paths resolve against that directory. Use `include` to select files with a glob pattern.

The `sandbox` that `createBashTool` returns is an AI SDK
[`Experimental_SandboxSession`](https://ai-sdk.dev/docs/reference/ai-sdk-core/sandbox)
for every backend, with `run`, `spawn`, `readFile`, `readBinaryFile`,
`readTextFile`, `writeFile`, `writeBinaryFile`, `writeTextFile` and `stat`, plus
our `dispose`. Every factory returns one directly, with `listDirectory` and
`deleteFile` too. The virtual sandbox uses the official
`@ai-sdk/sandbox-just-bash` adapter. Its `spawn` delivers output when the process
exits, so use a process-backed sandbox for live streaming.

Commands execute with Bash semantics. Process-backed
environments must contain `bash`; factories fail with a clear error when Bash
cannot be started. There is no POSIX `sh` fallback.

Every backend is also `AsyncDisposable`: it implements `[Symbol.asyncDispose]`
(which delegates to `dispose()`), so you can bind it with `await using` and let
the sandbox release at scope exit instead of writing `try/finally`:

```typescript
await using backend = await createDockerSandbox({ installers: [pkg(['jq'])] });
await backend.run({ command: 'jq --version' });
// backend.dispose() runs automatically when this scope exits
```

## One-off and chat sandboxes

Every factory makes a one-off, which nothing else reaches, and `dispose()`
removes it: Docker and Apple Container stop and remove its container,
Microsandbox its VM, and Daytona deletes its sandbox. Once `dispose()` is
called, every operation of these one-offs rejects with an `Error` that names
the sandbox. A one-off whose container, VM or Daytona sandbox was removed from
outside rejects every operation with `SandboxNotFoundError`.

A sandbox that a chat's next turn reaches again comes from the backend's
`SandboxEnvironment`. The environment names each chat's sandbox
from its `namespace` and the chat's id, so the caller never names it. Give each
app or deployment its own namespace: two environments with the same namespace
on one engine reach the same sandboxes.

- `open(chat)` returns a handle to the chat's sandbox. It attaches to the
  sandbox when it runs, starts it when it is stopped, and creates it when there
  is none. Two callers that open the same chat at once get the same sandbox.
  The environment's options apply only when `open` creates the sandbox.
- `delete(chat)` removes the sandbox and everything in it outside its volumes.
  It never starts the sandbox, never touches a volume, and resolves when there
  is no sandbox.
- `stop(chat)`, on a `StoppableSandboxEnvironment` only, stops the sandbox and
  keeps its files, so the next `open` or `resume` starts it again. It never
  starts the sandbox, and resolves when the sandbox is stopped or missing.

The handle, a `ChatSandbox`, is the sandbox session plus two methods:

- `resume()` starts the sandbox when it is stopped and resolves at once when it
  runs. It never creates a sandbox. When the sandbox is gone, or another sandbox
  now has its name, it rejects with `SandboxNotFoundError`. Every other operation
  of the handle also rejects so after `delete`, even after the chat is opened
  again: close the handle and open the chat again.
- `close()` (or scope exit with `await using`) releases what this process holds,
  such as the engine client or the VM connection. It never stops, starts or
  removes the sandbox. After `close()`, every operation of the handle rejects
  with an `Error`, not `SandboxNotFoundError`.

| Environment                        | `stop`                                             | `delete`                                  |
| ---------------------------------- | -------------------------------------------------- | ----------------------------------------- |
| `DockerSandboxEnvironment`         | `docker stop`; the container and its files stay    | `docker rm -f` with its anonymous volumes |
| `AppleContainerSandboxEnvironment` | `container stop`; the container and its files stay | `container delete --force`                |
| `MicrosandboxSandboxEnvironment`   | Stops the microVM and keeps its root filesystem    | The SDK's `destroy`                       |
| `DaytonaSandboxEnvironment`        | None: use the `lifecyclePolicy` create option      | Deletes the sandbox found by name         |
| `VirtualSandboxEnvironment`        | None: nothing runs between commands                | Drops the chat's in-memory filesystem     |

A chat's sandbox takes no installers: a second worker could reach it before
they finish, so what it needs belongs in its image. Its durable files, such
as uploads and what the agent creates, belong in volumes, because the rest is
lost when the sandbox is deleted. The Docker, Apple Container and Microsandbox
environments take `volumes: (chat) => [...]`, with bind mounts and external
volumes only. The Daytona environment takes no volumes yet. The virtual
environment keeps each chat's files in this process only.

## Quick start: Docker + Bash tool

The fastest path for giving an AI agent a bash tool that runs in Docker:

```typescript
import { groq } from '@ai-sdk/groq';

import { printer } from '@deepagents/agent';
import {
  type AvailableSkill,
  ContextEngine,
  InMemoryContextStore,
  agent,
  createBashTool,
  createDockerSandbox,
  pkg,
  role,
  skills,
  user,
} from '@deepagents/context';

const backend = await createDockerSandbox({
  installers: [pkg(['curl', 'jq'])],
});
const sandbox = await createBashTool({
  sandbox: backend,
  workingDirectory: '/skills/deploy',
  uploadDirectory: {
    source: '/opt/agent-skills/deploy',
  },
});

// The application owns the source and builds this catalog from its own
// manifest, database, or discovery logic.
const availableSkills: AvailableSkill[] = [
  {
    name: 'deploy',
    description: 'Deploy services safely.',
    path: '/skills/deploy/SKILL.md',
  },
];

try {
  const context = new ContextEngine({
    chatId: 'demo',
    userId: 'user-1',
    store: new InMemoryContextStore(),
  });

  context.set(
    role('You are a helpful assistant with bash access.'),
    skills(availableSkills),
    user('Use the most relevant skill to help me.'),
  );

  const assistant = agent({
    name: 'Assistant',
    sandbox,
    model: groq('gpt-oss-20b'),
    context,
  });

  await printer.stdout((await assistant.stream()).result);
} finally {
  await sandbox.sandbox.dispose();
}
```

## Quick start: Docker sandbox

For direct container control without AI agent wiring:

```typescript
import { createDockerSandbox, pkg } from '@deepagents/context';

const sandbox = await createDockerSandbox({
  image: 'bash:5.3-alpine3.24',
  installers: [pkg(['curl', 'jq'])],
  volumes: [
    {
      type: 'bind',
      hostPath: process.cwd(),
      containerPath: '/workspace',
      readOnly: true,
    },
  ],
  container: { HostConfig: { Memory: 512 * 1024 ** 2, NanoCpus: 1e9 } },
});

try {
  const result = await sandbox.run({ command: 'curl --version' });
  console.log(result.stdout);

  await sandbox.writeTextFile({
    path: '/tmp/hello.txt',
    content: 'Hello from Docker!',
  });

  const content = await sandbox.readTextFile({ path: '/tmp/hello.txt' });
  console.log(content);
} finally {
  await sandbox.dispose();
}
```

Or use `useSandbox` for automatic cleanup:

```typescript
import { useSandbox } from '@deepagents/context';

const output = await useSandbox(
  { installers: [pkg(['curl'])] },
  async (sandbox) => {
    const result = await sandbox.run({ command: 'curl --version' });
    return result.stdout;
  },
);
```

## Quick start: Binary bridges

Bridge specific host binaries into a just-bash virtual file system (no Docker needed):

```typescript
import { ReadWriteFs } from 'just-bash';

import {
  createBashTool,
  createBinaryBridges,
  createVirtualSandbox,
} from '@deepagents/context';

const bridges = createBinaryBridges(
  'node',
  { name: 'python', binaryPath: 'python3' },
  { name: 'git', allowedArgs: /^(status|log|diff|show)/ },
);

await using backend = await createVirtualSandbox({
  fs: new ReadWriteFs({ root: process.cwd() }),
  customCommands: bridges,
});

const { bash } = await createBashTool({ sandbox: backend });
```

Binary bridges resolve virtual paths to real host paths and use the host's `PATH` for binary resolution, while restricting access via optional `allowedArgs` regex.

## Quick start: Virtual sandbox

Use the virtual sandbox when an agent needs the standard bash/read/write tool
surface without Docker:

```typescript
import { InMemoryFs } from 'just-bash';

import { createBashTool, createVirtualSandbox } from '@deepagents/context';

const sandbox = await createBashTool({
  sandbox: await createVirtualSandbox({ fs: new InMemoryFs() }),
});

const result = await sandbox.sandbox.run({ command: 'echo "hello"' });
console.log(result.stdout); // hello
```

The virtual backend uses `just-bash`, so command execution and file IO stay
in-process while still exercising the same `createBashTool` path used by agents.
Pass `javascript: true` when the virtual sandbox should expose `js-exec` for
JavaScript execution without bridging a host `node` binary.

When you want command groups such as `sql run`, `tool validate`, or
`marker remind` inside a virtual sandbox, pass `customCommands` to
`createVirtualSandbox()` and build them with
[Subcommand Builders](/docs/context/subcommand).

## Bash tool schema

`createBashTool()` from `@deepagents/context` returns a bash tool whose input
schema requires `command` and a nonempty `reasoning` string. The AI SDK validates
model tool calls against this schema before executing the command.

```typescript
interface BashToolInput {
  command: string;
  reasoning: string;
}

type WrappedBashTool = Tool<BashToolInput, CommandResult>;
```

The tool uses only `command` for execution. The AI SDK records `reasoning` in
the `tool-call` input, so it remains visible for auditing. A model call missing
`reasoning` produces a `tool-error` before the command runs.

Calling `execute()` directly bypasses the AI SDK's runtime input validation.
Supply the full `BashToolInput` when invoking the tool manually:

```typescript
import { InMemoryFs } from 'just-bash';

import {
  type BashToolInput,
  createBashTool,
  createVirtualSandbox,
} from '@deepagents/context';

await using backend = await createVirtualSandbox({ fs: new InMemoryFs() });
const sandbox = await createBashTool({
  sandbox: backend,
});

const input: BashToolInput = {
  command: 'ls',
  reasoning: 'List files to find the entry point',
};

await sandbox.tools.bash.execute!(input, {
  toolCallId: 'list-files',
  messages: [],
});
```

Type-safe consumers can import `WrappedBashTool` and `BashToolInput` directly from `@deepagents/context`.

## Command metadata

A bash hook can return host-only metadata alongside an optional replacement
result. `createBashTool()` merges it with metadata already returned by sandbox
decorators such as `withStraceFileChanges()`.

```typescript
const sandbox = await createBashTool({
  sandbox: backend,
  onAfterBashCall: ({ command }) =>
    command.startsWith('sql ')
      ? { meta: { formattedSql: 'SELECT 1' } }
      : undefined,
});
```

`meta` is preserved in the raw tool result for host-side consumers and stripped
from model-visible output by the toolkit's shared toolset projection.

## Custom errors: `BashException`

Subclass `BashException` when you want a command or transform hook to fail with
an explicit `CommandResult` shape.

```typescript
import { BashException, type CommandResult } from '@deepagents/context';

class RateLimitError extends BashException {
  constructor(private readonly retryAfterMs: number) {
    super(`rate limited; retry in ${retryAfterMs}ms`);
  }

  format(): CommandResult {
    return {
      stdout: '',
      stderr: `${this.message}\n`,
      exitCode: 1,
    };
  }
}
```

`createBashTool()` catches `BashException` instances around sandbox execution
and returns `format()` to the caller. Other error types still propagate normally.

## Debug logging

Gate bash logging behind your own environment variable when you construct the
tool:

```bash
DEBUG_BASH=1 node scripts/run-demo.ts
# [bash] sql run main "SELECT 1"
# [bash] exit 1
```

The env var is gate-only — not a magic config:

```typescript
const debug = Boolean(process.env.DEBUG_BASH);

await createBashTool({
  sandbox: bashInstance,
  onBeforeBashCall: ({ command }) => {
    if (debug) console.log(`[bash] ${command}`);
    return { command };
  },
  onAfterBashCall: ({ result }) => {
    if (debug && result.exitCode !== 0) {
      console.log(`[bash] exit ${result.exitCode}`);
    }
    return { result };
  },
});
```
