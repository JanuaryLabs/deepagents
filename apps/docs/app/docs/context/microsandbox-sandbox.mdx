---
title: Microsandbox sandbox
description: Execute OCI images in local hardware-isolated microVMs without Docker daemon coupling
---

The Microsandbox backend runs commands inside local hardware-isolated microVMs
through the optional [`microsandbox`](https://www.npmjs.com/package/microsandbox)
SDK. It implements the same `DisposableSandbox` contract as the other
DeepAgents backends: the AI SDK sandbox session plus `dispose`.

Use it when you want standard OCI images and real process streaming, but do not
want your app coupled to a Docker daemon. The backend boots a microVM from an
image, creates the working directory, and returns a sandbox that can plug
directly into `createBashTool`.

<Callout type="warn">
  Microsandbox is an optional peer dependency. It requires Node.js 22+ and
  hardware virtualization: Apple silicon, Linux with KVM, or Windows with WHP.
</Callout>

## Installation

```npm
npm install microsandbox@^0.7.8
```

If the package or runtime is unavailable, `createMicrosandboxSandbox()` throws
`MicrosandboxNotAvailableError`. This includes an incomplete runtime installation.

## Basic usage

```typescript
import { createMicrosandboxSandbox } from '@deepagents/context';

await using sandbox = await createMicrosandboxSandbox();

const result = await sandbox.run({ command: 'echo "Hello from Microsandbox"' });
console.log(result.stdout);
```

The sandbox is an AI SDK `Experimental_SandboxSession` plus `dispose`. The
default image is `bash:5.3-alpine3.24`. The default working directory is
`/workspace`, and the factory creates it during boot because common images do
not ship that directory. Commands start there, and relative paths in every file
call resolve against it.

## AI agent integration

```typescript
import { createBashTool, createMicrosandboxSandbox } from '@deepagents/context';

const backend = await createMicrosandboxSandbox({
  configure: (builder) => builder.image('node:lts-bookworm-slim'),
});

const sandbox = await createBashTool({ sandbox: backend });
```

Pass the `sandbox.tools` object to an agent the same way you would with Docker,
Apple Container, Daytona, or a virtual sandbox.

## One-off and chat VMs

`createMicrosandboxSandbox` makes a one-off: a microVM under a generated name,
which nothing else reaches. Its `dispose()` stops and removes the microVM, and
every operation of the sandbox rejects once `dispose()` is called.

A microVM that outlives the process, so that the next turn of a chat finds its
files, is a chat's. A `MicrosandboxSandboxEnvironment` names it from a
namespace and the chat's id:

```typescript
import { MicrosandboxSandboxEnvironment } from '@deepagents/context';

const environment = new MicrosandboxSandboxEnvironment({
  namespace: 'analytics',
  image: 'python:3.12-slim',
  configure: (builder) => builder.memory(2048),
});

await using sandbox = await environment.open({
  chatId: 'chat-123',
  userId: 'user-456',
});
await sandbox.run({ command: 'echo kept > /workspace/note.txt' });
```

Every `open` of the chat reaches the same microVM. `close()` (or scope exit)
releases the handle and leaves the microVM running; `environment.stop(chat)`
stops it and keeps its root filesystem, and `environment.delete(chat)` removes
it.

The chat's microVM is persisted and detached, so it outlives the process that
opened it. It takes `image` without installers, `volumes` as a function of the
chat (`(chat) => [...]`, bind mounts and existing named volumes only), and
`configure` for the rest of the SDK builder, applied only when `open` creates
the microVM. Each handle holds its own connection to the microVM, which
`close()` detaches. See [one-off and chat sandboxes](/docs/context/sandbox#one-off-and-chat-sandboxes) for what `open`, `stop`, `delete`, `resume` and
`close` promise on every backend.

## Options

| Option           | Type                                 | Description                                                                                                                                          |
| ---------------- | ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workdir`        | `string`                             | Where commands start and relative paths resolve; defaults to `/workspace`                                                                            |
| `commandTimeout` | `number`                             | Per-command timeout for `run` and `spawn`, in milliseconds; the command exits 124                                                                    |
| `readiness`      | `(sandbox) => void \| Promise<void>` | Hook that must pass before the factory returns                                                                                                       |
| `configure`      | `(builder) => builder`               | Fluent access to the SDK builder: image (defaults to `bash:5.3-alpine3.24`), cpus, memory, env, volumes, network policy, secrets, user, idle timeout |

The options are the inputs the factory itself reads. Everything else is set
fluently on the SDK builder through `configure`.

The factory applies `workdir`, the Bash shell, and an ephemeral microVM that
is not detached after `configure`. A one-off is therefore removed on
`dispose()` even if `configure` calls `ephemeral(false)` or `detached(true)`,
and the factory's `workdir` wins over one set in `configure`.

## Command execution APIs

`run` is buffered and accepts an `abortSignal`. An abort kills the guest
process, and `run` rejects with the abort reason:

```typescript
const controller = new AbortController();
const pending = sandbox.run({
  command: 'sleep 30',
  abortSignal: controller.signal,
});
setTimeout(() => controller.abort(), 1_000);
await pending; // rejects
```

For live byte streams, use `spawn`. `kill()` stops the process; with
`stdin: true` the handle has a writable `stdin`:

```typescript
const proc = await sandbox.spawn({
  command: 'node long-task.js',
  workingDirectory: '/workspace',
});

const decoder = new TextDecoder();
for await (const chunk of proc.stdout) {
  process.stdout.write(decoder.decode(chunk, { stream: true }));
}
const { exitCode } = await proc.wait();
```

`run` lowers onto the same streaming path as `spawn`. A killed command exits
with `-1`, the code the SDK reports for any signal.

## Readiness hooks

Use `readiness` when the image needs a daemon or service started before the
agent gets the sandbox:

```typescript
const sandbox = await createMicrosandboxSandbox({
  configure: (builder) => builder.image('my-daemon-image:0.1.0'),
  readiness: async (sandbox) => {
    const result = await sandbox.run({ command: 'start-daemon && wait-ready' });
    if (result.exitCode !== 0) throw new Error(result.stderr);
  },
});
```

If `readiness` throws, the factory disposes the sandbox and rethrows the error.

## Image cache demo

The Text2SQL demo shows the local image-cache flow:

```bash
node demo/microsandbox-text2sql/bootstrap.ts
node demo/microsandbox-text2sql/demo-microsandbox.ts
```

`bootstrap.ts` exports the shared daemon image from Buildx as an OCI archive and
loads it directly into the local Microsandbox cache with the SDK's
`Image.load()`. The demo then uses
`createMicrosandboxSandbox({ configure })` with `image(...)` and `pullPolicy('never')` so a
missing local image fails clearly instead of trying a registry pull.

## Error handling

All package-owned errors extend `MicrosandboxSandboxError`:

| Error                           | When                                                                            |
| ------------------------------- | ------------------------------------------------------------------------------- |
| `MicrosandboxNotAvailableError` | The optional dependency is unavailable, or the runtime is missing or incomplete |
| `MicrosandboxCreationError`     | Sandbox creation fails outside a known SDK error                                |

The adapter wraps the SDK's `LibkrunfwNotFoundError`, `RuntimeNotInstalledError`,
and `RuntimeIncompleteError` in `MicrosandboxNotAvailableError`, retaining the
SDK error in `cause`. Other `MicrosandboxError` subclasses pass through unchanged,
so callers can handle those SDK failure classes directly. File calls reject with
the SDK's `SandboxFsOpsError`, except that a missing path resolves to `null` (or
`false` from `deleteFile`).
